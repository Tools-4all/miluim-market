# מילואימרקט - מדריך להגנת הפרויקט

המסמך מסביר כל דבר שיש בפרויקט, בשפה פשוטה. כדאי לקרוא אותו עם הקוד פתוח לידו.

---

## 1. מה הפרויקט עושה

**מילואימרקט** הוא שוק יד שנייה למילואימניקים. משתמש מתחבר עם חשבון גוגל ויכול:

- לראות את כל המודעות, לחפש ולסנן (קטגוריה, אזור, להסתיר מה שנמכר)
- לפרסם מודעה עם תמונה, מחיר (או "למסירה"), קטגוריה, מצב ואזור
- להיכנס למודעה, לשאול שאלה בתגובות (שכולם רואים), לשמור במועדפים
- **לשלוח למוכר הודעה פרטית** בתוך האתר ולנהל איתו שיחה (או לפנות בוואטסאפ, אם המוכר מילא טלפון)
- לראות את כל השיחות שלו, כקונה וכמוכר, בעמוד "הודעות"
- לראות פרופיל של מוכר עם כל המודעות שלו
- בפרופיל שלו: לעדכן טלפון, יחידה ועיר
- על מודעה שלו: לערוך, לסמן "נמכר" או למחוק

## 4. מושגי React שמופיעים בפרויקט

### קומפוננטה (Component)
פונקציה שמחזירה JSX (משהו שנראה כמו HTML). כל קובץ ב-`pages` וב-`components` הוא קומפוננטה.

```jsx
function Navbar() {
  return <nav>...</nav>
}
```

### JSX
הכתיב שנראה כמו HTML בתוך JavaScript. ההבדלים העיקריים:
- `className` במקום `class`
- סוגריים מסולסלים `{}` מכניסים קוד JavaScript: `<h1>{listing.title}</h1>`

### Props
מידע שקומפוננטת אב מעבירה לקומפוננטת בן, כמו פרמטרים של פונקציה.
```jsx
<ListingCard listing={item} />          // העמוד מעביר את המודעה
function ListingCard({ listing }) {...} // הכרטיס מקבל אותה
```

### State - `useState`
משתנה ש-React "זוכר", ו**כל שינוי בו מצייר את הקומפוננטה מחדש**.
```jsx
const [search, setSearch] = useState('')  // ערך התחלתי: מחרוזת ריקה
setSearch('וסט')                          // משנה את הערך → המסך מתעדכן
```
אסור לשנות state ישירות (`search = 'x'`), כי React לא ידע שהוא השתנה.

### `useEffect`
קוד שרץ **אחרי** שהקומפוננטה מופיעה על המסך. משתמשים בו לטעינת נתונים.
```jsx
useEffect(() => {
  loadListings()
}, [])      // [] = רק פעם אחת, כשהעמוד נטען
}, [id])    // [id] = בכל פעם ש-id משתנה
```
אם ה-useEffect מחזיר פונקציה, React מריץ אותה כשהקומפוננטה נעלמת. ככה מפסיקים להאזין ל-Firebase (ב-`AuthContext` וב-`Comments`).

### `useRef`
"מצביע" לאלמנט על המסך, שלא גורם לציור מחדש כשמשתמשים בו. בעמוד השיחה: `const bottomRef = useRef(null)`, ו-`<div ref={bottomRef} />` בסוף ההודעות. אחר כך `bottomRef.current.scrollIntoView()` גולל את השיחה לתחתית.

### Controlled input (שדה מבוקר)
כל שדה בטופס מחובר ל-state: `value` מה-state, ו-`onChange` מעדכן את ה-state.
```jsx
<input value={title} onChange={(e) => setTitle(e.target.value)} />
```

### רינדור מותנה (Conditional rendering)
```jsx
{user && <Link to="/new">פרסום</Link>}              // מוצג רק אם יש user
{user ? <button>התנתקות</button> : <button>התחברות</button>}   // זה או זה
```

### רשימות ו-`key`
```jsx
{filtered.map((item) => <ListingCard key={item.id} listing={item} />)}
```
`key` עוזר ל-React לדעת איזה פריט השתנה. משתמשים ב-id ייחודי.

### Context - `createContext` / `useContext`
דרך לשתף מידע עם **כל** הקומפוננטות בלי להעביר אותו ב-props בכל שלב. אצלנו `AuthContext` משתף את המשתמש המחובר. כל קומפוננטה כותבת:
```jsx
const { user, login, logout } = useAuth()
```
`useAuth` הוא **custom hook** שכתבנו: פונקציה קטנה שקוראת ל-`useContext(AuthContext)`.

### React Router
- `HashRouter` (ב-`main.jsx`) עוטף את כל האפליקציה
- `Routes` / `Route` (ב-`App.jsx`) מגדירים איזה עמוד מתאים לאיזו כתובת
- `Link` מעביר לעמוד אחר בלי לטעון את הדף מחדש
- `NavLink` (בסרגל הניווט) הוא כמו `Link`, אבל מוסיף את המחלקה `active` לקישור של העמוד שבו נמצאים. כך הקישור הנוכחי מודגש בצבע
- `useParams` קורא פרמטר מהכתובת: בכתובת `/listing/abc123`, `id` שווה `"abc123"`
- `useNavigate` מעביר עמוד מתוך קוד, למשל אחרי שמירת מודעה

**למה HashRouter ולא BrowserRouter?** האתר יעלה ל-GitHub Pages, שמגיש רק קבצים קבועים. עם BrowserRouter, רענון של `/listing/123` יחפש קובץ כזה בשרת ויחזיר 404. עם HashRouter הכתובת היא `/#/listing/123`, והחלק שאחרי ה-`#` לא נשלח לשרת בכלל.

## 5. מושגי JavaScript שמופיעים בפרויקט

- **`async` / `await`** - פעולות מול Firebase לוקחות זמן (הן עוברות ברשת). `await` אומר "חכה לתשובה ואז המשך". פונקציה שמשתמשת ב-`await` חייבת להיות `async`.
- **Promise** - "הבטחה" לתוצאה שתגיע בעתיד. כל פונקציה של Firebase מחזירה Promise. ב-`resizeImage.js` יצרנו Promise בעצמנו.
- **`Promise.all`** - ב-`Favorites.jsx`: שולח כמה בקשות במקביל ומחכה שכולן יחזרו.
- **`try` / `catch`** - ב-`ListingForm.jsx`: אם השמירה נכשלת, תופסים את השגיאה ומציגים הודעה.
- **`.map` / `.filter` / `.sort`** - עבודה עם מערכים. `filter` בסינון בעמוד הראשי, `map` להפיכת רשימה לכרטיסים.
- **Spread `...`** - `{ id: d.id, ...d.data() }` יוצר אובייקט חדש עם כל השדות של המסמך, ומוסיף לו את ה-id.
- **Optional chaining `?.`** - `seller?.phone`: אם `seller` הוא null לא תהיה שגיאה, פשוט יוחזר undefined.
- **Template literal** - `` `/listing/${id}` `` מכניס משתנה לתוך מחרוזת.
- **`import` / `export`** - כל קובץ הוא מודול. `export default` לדבר הראשי בקובץ, `export` רגיל לכמה דברים.

## 6. Firebase - איך הנתונים נשמרים

### Firestore בקצרה
Firestore הוא מסד נתונים **NoSQL**: אין טבלאות ושורות, יש:
- **אוסף (Collection)** - כמו תיקייה. לדוגמה `listings`.
- **מסמך (Document)** - כמו קובץ JSON בתוך התיקייה, עם id ייחודי.
- **תת-אוסף** - אוסף בתוך מסמך. אצלנו התגובות: `listings/{id}/comments`.

### מבנה הנתונים שלנו
```
users/{uid}
    name, photo          ← נשמרים בהתחברות (AuthContext)
    phone, unit, city    ← המשתמש ממלא בפרופיל
    favorites: [id, id]  ← מערך של מזהי מודעות

listings/{autoId}
    title, description, price, category, condition, region
    image                ← התמונה כטקסט Base64 (ראו סעיף 8)
    status: "active" / "sold"
    sellerId, sellerName
    createdAt            ← serverTimestamp()

listings/{id}/comments/{autoId}
    text, authorId, authorName, createdAt

chats/{listingId_buyerId}            ← שיחה פרטית בין קונה למוכר
    listingId, listingTitle
    sellerId, sellerName, buyerId, buyerName
    participants: [sellerId, buyerId]  ← מי מורשה לראות את השיחה
    lastMessage, lastSenderId, updatedAt
    unreadBy                           ← מי עוד לא קרא את ההודעה האחרונה (או null)

chats/{chatId}/messages/{autoId}
    text, senderId, createdAt
```

**למה ה-id של שיחה הוא `listingId_buyerId` ולא id אוטומטי?** כך לכל קונה יש בדיוק שיחה אחת לכל מודעה. כשהקונה לוחץ שוב על "שליחת הודעה למוכר", `setDoc` עם `merge: true` כותב לאותו מסמך ולא יוצר שיחה כפולה.

**למה `sellerName` נשמר בתוך המודעה, אם הוא כבר קיים ב-users?** כדי שבעמוד הראשי לא נצטרך לטעון את המוכר של כל מודעה בנפרד. שכפול מכוון כזה נפוץ במסדי NoSQL, וקוראים לו **דה-נורמליזציה**.

### הפונקציות של Firestore שבהן השתמשנו

| פונקציה | מה עושה | איפה |
|---|---|---|
| `collection(db, 'listings')` | הפניה לאוסף | בכל מקום |
| `doc(db, 'listings', id)` | הפניה למסמך אחד | עמוד מודעה, פרופיל |
| `getDocs(query)` | קריאה חד-פעמית של הרבה מסמכים | Home, Profile |
| `getDoc(docRef)` | קריאה של מסמך אחד | ListingDetails, Favorites |
| `onSnapshot` | **האזנה** - מתעדכן לבד בכל שינוי | Comments |
| `addDoc` | מסמך חדש עם id אוטומטי | פרסום מודעה, תגובה |
| `setDoc(..., { merge: true })` | כתיבה למסמך עם id ידוע, בלי למחוק שדות אחרים | AuthContext, Profile |
| `updateDoc` | עדכון שדות במסמך קיים | סימון "נמכר" |
| `deleteDoc` | מחיקה | מחיקת מודעה / תגובה |
| `query`, `where`, `orderBy` | סינון ומיון בצד של Firebase | Home, Profile, Comments |
| `arrayUnion` / `arrayRemove` | הוספה/הסרה ממערך בלי לקרוא אותו קודם | מועדפים |
| `serverTimestamp()` | הזמן לפי השעון של Firebase ולא של המחשב של המשתמש | createdAt |
| `timestamp.toDate()` | הופך זמן של Firebase לתאריך רגיל של JavaScript, ואז `toLocaleDateString('he-IL')` מציג אותו בפורמט ישראלי | "פורסם ב-" בעמוד מודעה |

**`getDocs` מול `onSnapshot`:** בעמוד הראשי מספיק לטעון פעם אחת. בתגובות רצינו שתגובה חדשה תופיע מיד, גם אם מישהו אחר כתב אותה, ולכן שם יש האזנה.

**למה בפרופיל המיון נעשה בדפדפן?** שאילתה שמשלבת `where` על שדה אחד עם `orderBy` על שדה אחר דורשת ב-Firestore "אינדקס מורכב" שצריך ליצור ידנית. כדי לשמור על פשטות, ממיינים אחרי שהנתונים הגיעו.

### התחברות (Authentication)
1. `signInWithPopup(auth, googleProvider)` פותח חלון של גוגל
2. גוגל מחזירה משתמש עם `uid` (מזהה קבוע), `displayName` ו-`photoURL`
3. אנחנו שומרים את השם והתמונה ב-`users/{uid}`, כדי שמשתמשים אחרים יוכלו לראות אותם
4. `onAuthStateChanged` מאזין לשינויים. גם כשמרעננים את הדף, Firebase זוכר את המשתמש ומודיע לנו
5. בזמן הבדיקה הזו `loading` שווה `true`, ו-`App.jsx` מציג "טוען...". בלי זה, לרגע היה נראה שהמשתמש לא מחובר.

## 7. אבטחה - כללי Firestore

**שאלה שכנראה תישאל: "המפתח של Firebase גלוי בקוד - זה לא מסוכן?"**

לא. ה-`apiKey` של Firebase רק **מזהה** את הפרויקט, הוא לא סיסמה. הוא חייב להגיע לדפדפן, ולכן כל אחד יכול לראות אותו. ההגנה האמיתית היא **כללי האבטחה** (`firestore.rules`), שרצים בשרת של גוגל ובודקים כל בקשה.

הכללים שלנו:
- **users** - כולם קוראים. רק המשתמש עצמו כותב למסמך שלו (`request.auth.uid == userId`)
- **listings** - כולם קוראים. ליצור: רק משתמש מחובר, ורק עם `sellerId` שלו. לעדכן ולמחוק: רק מי שפרסם
- **comments** - כולם קוראים. ליצור: רק משתמש מחובר בשם עצמו. למחוק: הכותב, או בעל המודעה. כדי לבדוק מי בעל המודעה, הכלל קורא את מסמך המודעה עם `get(...)`
- **chats** - רק מי שנמצא במערך `participants` (הקונה והמוכר) יכול לקרוא שיחה ולעדכן אותה, ואי אפשר לשנות את רשימת המשתתפים. רק הקונה פותח שיחה, ורק בשם עצמו
- **messages** - קוראים ושולחים רק משתתפי השיחה. כדי לבדוק את זה, הכלל קורא את מסמך השיחה עם `get(...)`. שולח יכול לשלוח הודעה רק בשם עצמו (`senderId`)

בכללים:
- `request.auth` - מי שולח את הבקשה (`null` = לא מחובר)
- `resource.data` - המסמך כמו שהוא עכשיו
- `request.resource.data` - המסמך כמו שיהיה אחרי השינוי

**למה לא מספיק להסתיר את כפתור "מחיקה" בקוד React?** כי כל אחד יכול לפתוח את כלי הפיתוח בדפדפן ולשלוח בקשה ישר ל-Firebase. הסתרת הכפתור היא רק נוחות. הכללים הם מה שבאמת מונע מחיקה.

## 8. תמונות - למה Base64 ולא Firebase Storage

Firebase Storage הוא המקום הרגיל לקבצים, אבל בפרויקטים חדשים הוא דורש להגדיר כרטיס אשראי (תוכנית Blaze). לכן:

1. המשתמש בוחר קובץ (`<input type="file">`)
2. `resizeImage.js` קורא אותו עם `FileReader`, מצייר אותו על `<canvas>` ברוחב של עד 800 פיקסלים, ושומר כ-JPEG באיכות 70%
3. `canvas.toDataURL` מחזיר את התמונה כ**טקסט** (Base64) שמתחיל ב-`data:image/jpeg;base64,...`
4. הטקסט נשמר בשדה `image` של המודעה, ו-`<img src={listing.image}>` יודע להציג אותו

**המגבלה:** מסמך ב-Firestore מוגבל ל-1MB. אחרי הקטנה תמונה שוקלת בערך 50-150KB, אז זה מספיק לתמונה אחת למודעה. באפליקציה אמיתית הייתי עובר ל-Storage.

## 9. מסלול של פעולה מקצה לקצה - "פרסום מודעה"

כדאי להכיר את המסלול הזה בעל פה. הוא מראה איך כל החלקים מתחברים:

1. המשתמש לוחץ "+ פרסום מודעה" ב-`Navbar`. ה-`Link` משנה את הכתובת ל-`/#/new`
2. `App.jsx` רואה את הכתובת ומציג את `ListingForm`
3. `ListingForm` בודק דרך `useAuth()` שיש משתמש מחובר, ובודק שאין `id` בכתובת - כלומר זו מודעה חדשה ולא עריכה
4. כל הקלדה בשדה מפעילה `onChange`, שמעדכן state, ו-React מצייר את השדה מחדש עם הערך החדש
5. בחירת תמונה מפעילה את `resizeImage`, והתוצאה נשמרת ב-state `image` (ומוצגת תצוגה מקדימה)
6. בלחיצה על "פרסום": `handleSubmit` קורא ל-`e.preventDefault()` (שלא ירענן את הדף) ובודק שיש כותרת
7. `addDoc` שולח את המודעה ל-Firestore
8. בשרת, כללי האבטחה בודקים שהמשתמש מחובר ושה-`sellerId` שלו
9. Firestore מחזיר את ה-id החדש, ו-`navigate` מעביר לעמוד המודעה
10. `ListingDetails` קורא את ה-id מהכתובת עם `useParams` וטוען את המודעה עם `getDoc`

## 10. שאלות שכדאי להתכונן אליהן

**מה ההבדל בין props ל-state?**
props מגיעים מבחוץ (מקומפוננטת האב), ואי אפשר לשנות אותם. state הוא של הקומפוננטה עצמה, והיא יכולה לשנות אותו עם פונקציית ה-set.

**למה צריך useEffect? למה לא לטעון את הנתונים ישר בגוף הפונקציה?**
הקומפוננטה רצה מחדש בכל שינוי state. אם הטעינה הייתה בגוף הפונקציה, היא הייתה רצה כל פעם, מעדכנת state, וגורמת לעוד ריצה, בלולאה אינסופית. `useEffect` עם `[]` מבטיח שהטעינה תרוץ פעם אחת.

**מה זה מערך התלויות (dependency array) ב-useEffect?**
הרשימה בסוף ה-useEffect. האפקט ירוץ מחדש רק כשאחד מהערכים ברשימה משתנה. ב-`ListingDetails` זה `[id]`: אם עוברים ממודעה למודעה, הנתונים נטענים מחדש.

**למה Context ולא props?**
כמעט כל הקומפוננטות צריכות לדעת מי מחובר. עם props היינו צריכים להעביר את `user` דרך כל שכבה, גם דרך קומפוננטות שלא צריכות אותו בעצמן ("prop drilling").

**איך הסינון עובד? הוא שולח שאילתה ל-Firebase?**
לא. טוענים את כל המודעות פעם אחת, וכל שינוי בשדה החיפוש מעדכן state. React מצייר מחדש, ו-`filter` רץ על המערך שכבר נמצא בדפדפן. זה מהיר ולא עולה קריאות נוספות. עם אלפי מודעות היה עדיף לסנן ב-Firebase עם `where`.

**מה קורה אם מישהו לא מחובר ומנסה להיכנס ל-`/new`?**
הקומפוננטה מציגה "צריך להתחבר". וגם אם מישהו יעקוף את זה, כללי האבטחה יחסמו את השמירה.

**איך עובדות ההודעות הפרטיות?**
1. בעמוד מודעה, "שליחת הודעה למוכר" יוצר (או פותח מחדש) מסמך שיחה `chats/{listingId_buyerId}` עם שני המשתתפים, ועובר לעמוד `Chat`.
2. `Chat` מאזין להודעות עם `onSnapshot`, כך שהודעה שהצד השני שולח מופיעה מיד, בלי לרענן.
3. שליחת הודעה: `addDoc` מוסיף מסמך לתת-האוסף `messages`, ו-`updateDoc` מעדכן במסמך השיחה את ההודעה האחרונה ואת הזמן.
4. בעמוד "הודעות" (`Chats`), השאילתה `where('participants', 'array-contains', user.uid)` מביאה את כל השיחות שהמשתמש משתתף בהן, כקונה וכמוכר.
5. `useRef` שומר הפניה לאלמנט בתחתית השיחה, ו-`scrollIntoView` גולל אליו בכל פעם שמגיעה הודעה.

**איך עובד המונה של ההודעות שלא נקראו?**
במסמך של כל שיחה יש שדה `unreadBy`:
1. כששולחים הודעה, `Chat` שם ב-`unreadBy` את ה-uid של **הצד השני**, כי הוא עוד לא קרא אותה.
2. ב-`Navbar` יש `onSnapshot` על כל השיחות של המשתמש. בכל שינוי סופרים כמה שיחות יש בהן `unreadBy` ששווה למשתמש המחובר, ושומרים ב-state `unreadCount`. אם הוא גדול מ-0, מוצג עיגול אדום עם המספר ליד "הודעות".
3. כשהמשתמש פותח את השיחה, `Chat` רואה ש-`unreadBy` הוא הוא, ומעדכן אותו ל-`null`. ה-`onSnapshot` שב-`Navbar` מקבל את השינוי, והמונה יורד לבד.

המונה סופר **שיחות** עם הודעה חדשה, לא כל הודעה בנפרד (כמו בוואטסאפ, שמציג כמה צ'אטים לא נקראו). הספירה נעשית בדפדפן ולא בשאילתה, כי שילוב של `array-contains` עם תנאי נוסף דורש ב-Firestore אינדקס מורכב.

**מה ההבדל בין תגובות להודעות?** תגובות ציבוריות: כולם רואים אותן, כמו שאלות מתחת למודעה. הודעות פרטיות: רק הקונה והמוכר רואים אותן, וכללי האבטחה אוכפים את זה.

**איך אותו טופס משמש גם לפרסום וגם לעריכה?**
ב-`App.jsx` שתי כתובות מציגות את אותה קומפוננטה: `/new` ו-`/edit/:id`. בתוך `ListingForm`, `useParams()` מחזיר `id` רק בכתובת של עריכה, ולכן `isEdit = Boolean(id)`. במצב עריכה, `useEffect` טוען את המודעה עם `getDoc` וממלא את ה-state של השדות, ובשמירה קוראים ל-`updateDoc` במקום ל-`addDoc`. `updateDoc` משנה רק את השדות שנשלחו, אז המוכר, הסטטוס ותאריך הפרסום לא משתנים. ככה לא כותבים את אותו טופס פעמיים (עיקרון **DRY** - Don't Repeat Yourself).

**מה מונע ממשתמש לערוך מודעה של מישהו אחר?**
שתי שכבות: בקוד, `ListingForm` מציג "אפשר לערוך רק מודעות שפרסמת" אם `sellerId` של המודעה שונה מהמשתמש המחובר. ובשרת, כלל `allow update` ב-`firestore.rules` מאשר עדכון רק לבעל המודעה, וגם לא נותן לשנות את `sellerId`.

**מה קורה לתגובות כשמוחקים מודעה?**
ב-Firestore, מחיקת מסמך **לא** מוחקת את תת-האוסף שלו. לכן `deleteListing` קודם טוען את כל התגובות עם `getDocs`, מוחק את כולן עם `Promise.all`, ורק אז מוחק את המודעה. בלי זה היו נשארות במסד "תגובות יתומות".

**מה יקרה כשמודעה שמורה במועדפים נמחקת?**
ב-`Favorites` יש `.filter((s) => s.exists())`, אז מודעה שנמחקה פשוט לא תוצג.

**מה זה `serverTimestamp`, ולמה לא `new Date()`?**
השעון של המחשב של המשתמש יכול להיות לא נכון. `serverTimestamp` מבקש מ-Firebase לרשום את השעה שלו, כך שכל המודעות ממוינות לפי אותו שעון.

**מה הייתי משפר בגרסה הבאה?**
העלאת תמונות ל-Storage (כמה תמונות למודעה), התראות בדחיפה (push) כשהאתר סגור, דירוג מוכרים, ו-pagination (טעינה בחלקים) כשיש הרבה מודעות.

## 11. העיצוב - איך ה-CSS בנוי

כל העיצוב נמצא בקובץ אחד, `src/index.css`, בלי ספריות עיצוב. הרעיונות העיקריים:

- **משתני CSS** - בראש הקובץ, בתוך `:root`, מוגדרים פעם אחת כל הצבעים והמידות: `--primary: #3d4a2a`. בכל שאר הקובץ כותבים `var(--primary)`. כדי לשנות את הצבע של כל האתר, משנים שורה אחת.
- **שפה עיצובית אחידה** - ירוק זית כהה כצבע ראשי, רקע בהיר, קופסאות לבנות (`.panel`) עם מסגרת דקה, צל עדין ופינות מעוגלות. אותם רכיבים חוזרים בכל העמודים, ולכן האתר נראה רציני ומסודר.
- **סוגי כפתורים** - כפתור ראשי (ירוק) לפעולה החשובה בכל מסך, ו-`button-secondary`, `button-ghost` ו-`button-danger` לפעולות משניות, פחות חשובות ומסוכנות (מחיקה).
- **Flexbox** (`display: flex`) - מסדר אלמנטים בשורה או בעמודה. משמש בסרגל הניווט, בכפתורים ובטפסים.
- **Grid** (`display: grid`) - רשת המודעות: `repeat(auto-fill, minmax(240px, 1fr))` אומר "כמה עמודות שנכנסות, כל אחת לפחות 240 פיקסלים". לכן במחשב רואים 4 כרטיסים בשורה ובטלפון אחד, בלי לכתוב קוד נפרד.
- **`aspect-ratio: 4 / 3` ו-`object-fit: cover`** - כל התמונות בכרטיסים באותו גודל, גם אם המשתמש העלה תמונה לרוחב או לגובה. התמונה ממלאת את המסגרת בלי להימתח.
- **`position: sticky`** - סרגל הניווט נשאר למעלה גם כשגוללים.
- **`:focus` ו-`:hover`** - שדה שמקלידים בו מקבל מסגרת ירוקה, וכרטיס עולה קצת כשהעכבר עליו. זה נותן למשתמש משוב.
- **Media query** - `@media (max-width: 760px) { ... }`: הכללים בפנים חלים רק במסך צר. בטלפון הקישורים בסרגל יורדים לשורה שנייה, וטפסים ועמוד המודעה עוברים לעמודה אחת. זה נקרא **עיצוב רספונסיבי**.
- **מצבים מיוחדים** - לכל עמוד יש עיצוב גם ל"טוען..." (`.loading`), למצב שאין תוצאות (`.empty`) ולשגיאה (`.error`), כדי שהמשתמש תמיד יבין מה קורה.
- **מודעה שנמכרה** - הכרטיס מקבל את המחלקה `card-sold`: התמונה הופכת אפורה (`filter: grayscale`) ומופיעה עליה תווית "נמכר".

## 12. הרצה והעלאה לאינטרנט

```bash
npm install     # התקנת הספריות (פעם אחת)
npm run dev     # הרצה במחשב - נפתח בכתובת http://localhost:5173/miluim-market/
npm run build   # בניית האתר לקבצים סופיים בתיקייה dist
npm run deploy  # בנייה והעלאה ל-GitHub Pages
```

**האתר באוויר:** https://tools-4all.github.io/miluim-market/

**איך ההעלאה עובדת:**
1. `vite build` הופך את כל קבצי ה-React לקבצי HTML, CSS ו-JavaScript רגילים בתיקייה `dist`. דפדפן לא מבין JSX, אז צריך את השלב הזה.
2. הספרייה `gh-pages` מעלה את התיקייה `dist` לענף נפרד בריפו בשם `gh-pages`.
3. GitHub Pages מגיש את הקבצים מהענף הזה, ככה שהאתר זמין בקישור.

**שלושה דברים שהיה צריך להגדיר בשביל זה:**
- `base: '/miluim-market/'` ב-`vite.config.js` - האתר יושב בתת-תיקייה של הדומיין, אז כל הקישורים לקבצים צריכים את הקידומת הזו.
- `HashRouter` (סעיף 4) - בלי שרת, רענון של עמוד פנימי היה מחזיר 404.
- ב-Firebase Authentication הוספתי את `tools-4all.github.io` לרשימת **Authorized domains**. Firebase מאפשר התחברות עם גוגל רק מכתובות שברשימה, כדי שאתר אחר לא יוכל להתחזות לאתר שלנו.

**איפה הגדרות ה-Firebase?** בקובץ `.env.local`, שלא עולה ל-GitHub (הוא ב-`.gitignore`). בזמן `npm run deploy` הבנייה נעשית במחשב, ו-Vite מכניס את הערכים לקוד שנבנה. מי שמוריד את הקוד מ-GitHub צריך ליצור לעצמו `.env.local` משלו.
